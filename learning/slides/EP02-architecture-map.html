为什么要拆

规模变大后，三个矛盾逼着我们拆分

  1. 想象一个只有几百个用户的交易所。一个程序，加一个数据库，就能跑起来。所有逻辑在一个进程里，所有数据在一个库里，开发起来最简单。
  2. 规模变大以后，第一个矛盾出现：速度和正确。撮合要在微秒内完成，账本写入却要等数据库事务提交。
  3. 两件事放在一个程序里，快的会被慢的拖住。所以撮合引擎和账本必须分开。
  4. 第二个矛盾是在线和离线。链上确认要几秒到几十分钟，用户下单却要毫秒级响应。所以链上层全部改成异步。
  5. 第三个矛盾是用户和员工。用户接口要扛高并发，运营后台要强权限和审计。所以两者也要分开。
  6. 但拆分有代价，叫分布式一致性。一笔交易跨 5 个服务，任何一个失败，都需要补偿。这是下一集的重点。

不成立之处：真实服务靠网络和消息通信，任何一段都可能慢或断。
  1. 先打个比方。交易所像一家大型银行网点。门口的保安和叫号机是接入层，检查身份，控制人流。
  2. 柜员是订单服务，接收你的申请。风控主管站在柜员旁边。金额太大或者行为可疑，他就喊停。
  3. 会计室是账本。每一笔钱的进出，都用借方和贷方两支笔，同时记在总账上。
  4. 交易大厅的拍卖师是撮合引擎，他只喊价、配对，不碰钱。金库和押运车，是钱包和链上层。后台办公室，就是运营后台。
  5. 记住一句话。拍卖师喊得再快，也要等会计室记完账，钱才算真正换了手。
  6. 比喻在哪里不成立？网点里大家在同一栋楼，喊一声就听见。真实系统靠网络和消息通信，任何一段都可能变慢或中断。
系统视角 · 六层架构 业界通用做法

六层架构全景

  1. 来看全景。币安没有公开完整架构，我们用业界通用的六层模型。服务名取自本系列的教学仓库。从上到下，越往下越靠近钱。
  2. 第一层是接入层。用户前端和量化程序，都先打到 API 网关。网关负责鉴权、限流，还有 WebSocket 长连接。
  3. 第二层是交易核心。订单服务管订单的生命周期，风控做下单前检查。撮合引擎在内存里配对，结算服务把成交写成账。
  4. 第三层是资金层。账本是双分录记账，钱包管充值和提币的单据，身份服务管用户、2FA 和 KYC。
  5. 第四层是链上层。索引器扫描区块，数确认数。托管适配器负责签名和广播。它们直接和区块链节点打交道。
  6. 第五层是数据层。PostgreSQL 存账，Redis 做缓存和限流。Kafka 是事件总线，ClickHouse 存行情历史。行情服务也放在这一层。
  7. 最后是第六层，运营后台。员工在这里审核提币、做对账、处理故障恢复。它能调用钱包、账本和订单服务。
读图要点

这张图里，最值得记住的三条连线

局限：图里省略了监控、配置中心、服务发现，以及合规、客服、清算对账等十几个系统。
  1. 这张图里，有三条连线最值得记住。第一条，撮合引擎不直接写账本。成交结果先交给结算服务，再由结算写账本。
  2. 为什么？撮合只负责配对，就像拍卖师只喊价，不碰钱。钱的变化，必须经过账本的校验和记录。如果撮合直接改余额，它就要同时追求快和对，两头都做不好。
  3. 第二条，账本是全图唯一的资金事实源。其他服务里看到的余额，都只是缓存或者副本。比如网关缓存的余额只用来快速展示，真正扣款时以账本为准。
  4. 第三条，链上层只和钱包服务打交道。交易核心完全不碰区块链。所以链再慢，也拖不垮交易。
  5. 这张图也有局限。它省略了监控、配置中心和服务发现。真实交易所还有合规、客服、清算对账等十几个系统。
每层的性能与一致性 示例目标

越靠近用户越快，越靠近资金越对

  1. 每一层对速度和一致性的要求，差别非常大。我们把延迟目标画在对数坐标上，这些都是示例目标。
  2. 最快的是撮合，小于 1 毫秒，是微秒级。它要求确定性：同样的输入，必须得到同样的输出。
  3. 接入层和订单风控，目标在 10 毫秒以内。接入层本身无状态，订单状态则要强一致。
  4. 账本慢一些，小于 50 毫秒。但它的要求最严：强一致，而且可审计。
  5. 行情小于 100 毫秒，只要求最终一致。K 线晚一点出来，不影响任何人的钱。
  6. 钱包和运营后台是秒级。钱包要强一致和幂等，同一笔充值不能入账两次。链上层最慢，从几秒到几个小时，因为要等确认数。
  7. 规律是这样的。越靠近用户的层越追求快，越靠近资金的层越追求对。链上层最慢，但它可以暂停，不会拖垮交易。
数字推演 示例

一笔下单的同步链路，延迟上限是多少？

  1. 用表里的示例目标算一笔账。一笔下单，同步要经过网关、订单风控、账本冻结、撮合四段。用户要等这四段都走完，才能拿到响应。
  2. 网关 10 毫秒，订单和风控再加 10 毫秒，累计 20 毫秒。
  3. 账本冻结 50 毫秒，撮合不到 1 毫秒。加起来，上限大约 71 毫秒。
  4. 如果把行情推送也塞进同步链路，再加 100 毫秒，就变成 171 毫秒。延迟翻了一倍多。
  5. 如果把链上确认也放进来，一笔下单要等几分钟。所以行情和链上，都必须放在同步链路之外。这就是前面说的，链上层全部异步。
故障与边界 · 单点

拆完以后，弱点在哪里

位置问题业界缓解办法
撮合引擎单线程处理一个交易对按交易对分片，热门交易对独占机器
撮合引擎状态在内存，宕机丢订单簿顺序日志 + 快照 + 重放
账本数据库主库宕机，资金操作全停主从切换，按用户分库
Kafka消费者堆积，推送延迟加分区、加消费者、告警
热钱包私钥泄露，资产被盗冷热分离、MPC、限额
网关行情剧烈波动，请求暴增限流、降级、排队
  1. 拆分以后，我们来找系统的弱点。先看撮合引擎。它用单线程处理一个交易对，吞吐受 CPU 单核速度限制。办法是按交易对分片，热门交易对独占一台机器。
  2. 撮合的状态在内存里，宕机后订单簿就丢了。所以要写顺序日志，定期做快照，重启后重放日志恢复。
  3. 账本数据库的主库也是单点。主库一宕机，所有资金操作都停。办法是主从切换，再按用户分库。
  4. Kafka 的消费者一旦堆积，余额和行情推送就会延迟。办法是加分区、加消费者，并设置告警。
  5. 热钱包的私钥一旦泄露，资产直接被盗。网关在行情剧烈波动时请求暴增，要靠限流、降级和排队扛住。
故障与边界 · 热点 示例数字

手续费账户：所有成交都要写它

  1. 再看热点。最典型的是手续费账户。每一笔成交，都要给手续费账户记一笔。
  2. 假设每秒 1 万笔成交，这是示例数字。1 万次写入，全都要锁同一行记录，只能一个一个排队。交易越活跃，队伍越长。
  3. 业界的做法是把它拆成多个子账户。拆成 16 个，每个子账户每秒只承担 625 次写入。
  4. 代价在对账。算手续费总收入时，要把 16 个子账户加起来。另一种缓解办法是批量记账，攒一批再写一次。
  5. 注意，热点不只出现在手续费账户。做市商账户、热门交易对的撮合线程，都可能成为热点。思路都一样：先找到被所有请求争抢的那一个点，再把它拆开。

  1. 来看币安的公开信息。币安上线时宣称，撮合引擎每秒能处理约 140 万笔订单。这是早期公开宣传，多家媒体转述过。
  2. 2020 年，币安完成了一次大规模撮合引擎升级。据媒体报道，新引擎用新的编程语言重写，性能提升约 10 倍。
  3. 币安还在多个司法辖区持牌或注册，为部分地区提供独立站点。比如 Binance US，是一家独立公司。
  4. 下面是业界通用做法，币安没有完整公开。每个交易对固定到一个撮合线程，再按交易对分片到多台机器。一个交易对内部不用加锁，顺序天然确定。
  5. 撮合做主备热备。所有输入先写进顺序日志，备机重放日志，保持和主机一致。
  6. 账本按用户 ID 分库分表。行情走多级扇出，接入层用全球 CDN 和多地域网关。提醒一句，网上流传的币安架构图，大多是推测。
本集小结

记住三件事

  • 按资金正确性拆服务：撮合求快，账本求对，钱包求安全。
  • 账本是唯一资金事实源；撮合不写账，链上只连钱包。
  • 越近用户越快，越近资金越对；单点靠分片和重放，热点靠拆账户。

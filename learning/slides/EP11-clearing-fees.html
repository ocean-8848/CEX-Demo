成交之后：清算、结算与手续费

TradeExecuted · A ⇄ B · 0.04 BTC @ 60,000

把撮合的一句话，翻译成账本里的钱。

拍卖师落槌 = 撮合
一秒钟，喊一声成交
财务室 = 结算
扣款、转账、收佣金，一分不差
比喻不准之处：真实的财务室是程序，每秒大量成交，且一笔都不能重复
  1. 撮合引擎只会说一句话。A 和 B 以 60000 的价格，成交了 0.04 BTC。可是 A 的钱什么时候扣？B 的币什么时候到？平台收多少手续费？
  2. 把这句话翻译成账本里的钱，就是清算和结算。这一集我们讲成交之后发生的一切。
  3. 打个比方。撮合像拍卖师落槌喊成交。结算像拍卖行的财务室。它从买家押金里扣款，把货款减去佣金转给卖家，佣金进拍卖行的账户。
  4. 落槌只要一秒，财务室必须一分不差。比方不准的地方是，交易所的财务室是程序。它每秒要处理大量成交，而且一笔都不能重复。

01 · Clearing vs Settlement

一个只算账，一个动钱

清算 Clearing

计算每一方应收、应付多少
只算账，不动钱

结算 Settlement

按清算结果修改账本余额
动钱 · 现货中两者连续完成

原子性

买方拿到币，卖方拿到钱

准确性

最小单位，规则舍入

不重不漏

每笔结算且仅一次
用户余额逐笔实时结算（币安现货属于这一类）· 手续费汇总、返佣可批量结算
  1. 先分清两个词。清算，是计算每一方应收多少、应付多少。它只算账，不动钱。
  2. 结算，是按清算结果，实际修改账本余额。它动钱。在现货交易所，两者通常在同一个服务里连续完成，所以我们合称结算。
  3. 成交以后，平台必须保证三件事。第一，原子性。买方拿到币，卖方拿到钱，不能只完成一半。
  4. 第二，准确性。金额精确到最小单位，手续费按规则计算和舍入。第三，不重不漏。每一笔成交，结算且只结算一次。
  5. 还有一个设计选择。加密现货的用户，期待成交后马上能卖，所以用户余额通常逐笔实时结算。币安现货属于这一类。平台内部的手续费汇总和返佣，可以批量结算。
02 · 成交之后发生什么 · 业界通用做法

从撮合引擎到用户的手机

  1. 来看成交之后的链路。撮合引擎产生成交事件 T1，写入消息队列。消息队列把 T1 投递给结算服务，注意是至少投递一次。
  2. 结算服务先做幂等检查，看 T1 是不是已经结算过。然后计算成交额和双方的手续费。
  3. 接着调用账本，记两组分录。一组是基础资产 BTC，幂等键 T1 base。一组是计价资产 USDT，幂等键 T1 quote。账本在同一个事务里，写流水、快照和 outbox。
  4. 账本成功以后，结算服务把 T1 标记为已结算，最后才向消息队列确认消费。如果中途崩溃，消息会重投，幂等键保证不会重复记账。
  5. 余额变化事件走 outbox，经消息队列到推送服务。推送服务再用 WebSocket 推给用户。所以推送可能比账本晚几十到几百毫秒，这是示例量级。界面短暂显示旧余额，是正常现象。

  1. 下面是本集的重头戏。示例数值：用户 A 先挂买单，0.1 BTC，价格 60000 USDT。A 是挂单方 Maker，下单时已冻结 6000 USDT。
  2. 用户 B 后下卖单，立即成交 0.04 BTC。B 是吃单方 Taker。成交额等于 60000 乘以 0.04，也就是 2400 USDT。
  3. 费率按普通用户示例，Maker 和 Taker 都是千分之一。规则是，手续费从收到的资产里扣。
  4. A 收到的是 BTC，所以付 BTC 手续费。0.04 乘以千分之一，等于 0.00004 BTC。
  5. B 收到的是 USDT，所以付 USDT 手续费。2400 乘以千分之一，等于 2.4 USDT。
03 · BTC 分录 · 幂等键 T1:base · 示例

B 交出 BTC，A 收到净额

  1. 先写 BTC 这一组分录，幂等键是 T1 base。我们一行一行来。
  2. 第一行，借用户 B 的 BTC 可用 0.04，B 交出 BTC。第二行，贷清算中间户 0.04，币进入清算户。
  3. 第三行，借清算中间户 0.04，币从清算户转出。
  4. 第四行，贷用户 A 的 BTC 可用 0.03996，这是 A 收到的净额。第五行，贷平台手续费收入 0.00004，这是 A 的 Maker 手续费。
  5. 合计一下。借方 0.08，贷方 0.08，平衡。清算中间户进了 0.04，又出了 0.04，余额归零。
03 · USDT 分录 · 幂等键 T1:quote · 示例

从 A 的冻结扣款，B 收到净额

  1. 再写 USDT 这一组，幂等键是 T1 quote。
  2. 第一行，借用户 A 的 USDT 冻结 2400，扣减 A 下单时冻结的钱。第二行，贷清算中间户 2400。
  3. 第三行，借清算中间户 2400。第四行，贷用户 B 的 USDT 可用 2397.6，这是 B 收到的净额。
  4. 第五行，贷平台手续费收入 2.4，这是 B 的 Taker 手续费。借方 4800，贷方 4800，平衡。
  5. 成交以后，A 的冻结还剩 3600，订单剩下的 0.06 BTC 继续挂在簿上。平台热钱包没有任何变化。成交只是负债在用户之间重新分配，再有一小部分变成平台收入。
  6. 两个提醒。第一，B 直接从可用余额卖出，是简化写法。真实系统里，B 的卖单也要先冻结。第二，如果漏写了第五行，借贷不平，账本必须拒绝提交。

Maker 挂单方 · A

订单进入订单簿等待成交 → 提供流动性

Taker 吃单方 · B

立即与簿上挂单成交 → 消耗流动性
通常 Maker 费率 ≤ Taker 费率
挂单多 → 簿更厚 → 滑点小 → 更多 Taker
  1. 刚才 A 是 Maker，B 是 Taker。挂单方 Maker，是订单进入订单簿等待成交的一方。它给市场提供了流动性。
  2. 吃单方 Taker，是订单立即和簿上已有挂单成交的一方。它消耗了流动性。B 的卖单一进来，就吃掉了 A 挂在 60000 的买单。
  3. 交易所通常让 Maker 费率小于等于 Taker 费率。原因是，挂单越多，订单簿越厚，滑点越小，就会有更多 Taker 愿意来交易。

商业逻辑：给 BNB 创造持续的使用需求，平台币的典型设计
  1. 第三个机制，BNB 抵扣。用户开启使用 BNB 抵扣以后，系统按折后费率计算手续费。折后费率是原费率乘以 75%。
  2. 然后把手续费按当时价格折算成 BNB，从用户的 BNB 可用余额里扣除。如果 BNB 不够，就按原费率，从收到的资产里扣。
  3. 算一下。B 的 Taker 手续费原本是 2.4 USDT。乘以 75%，是 1.8 USDT。假设 BNB 价格是 600 USDT，这只是示例，那就扣 0.003 BNB。
  4. 在账本里，这会多出一组 BNB 分录。借用户 B 的 BNB 可用，贷平台手续费收入 BNB。这时 USDT 分录里，就不再扣那 2.4 了。
  5. 商业逻辑是，BNB 抵扣给 BNB 创造了持续的使用需求。这是交易所平台币的典型设计。

  1. 第四个机制，返佣。老用户分享推荐码。新用户注册以后，平台把新用户手续费的一部分，返给推荐人，或者返给新用户本人。
  2. 据第三方公开整理，币安现货推荐的基础返佣比例是 20%。推荐人持有至少 500 BNB 时，最高可以到 40%。2024 年起，部分地区的基础比例下调到 10% 到 15%。这些不是官方数字，以官网为准。
  3. 推荐人还可以把一部分返佣让给被推荐人，这叫返现。示例：标准费率千分之一，被推荐人拿到 20% 返现，实际费率就是万分之八。
  4. 账本上，业界通常这样做。成交时，手续费先全部进平台手续费收入。返佣服务按周期汇总，比如每小时或者每天，这是示例。然后记一笔分录，借手续费收入或者返佣支出，贷推荐人可用。批量返佣还降低了手续费账户的热点压力，热点账户上一集讲过。

  1. 第五个机制，零手续费。根据币安官方公告。2022 年 7 月 8 日，币安对 13 个 BTC 现货交易对取消了手续费。其中包括 BTC 对 USDT，和 BTC 对 BUSD。

05 · 结算失败与补偿 · 业界通用做法

只能补，不能退回撮合之前

  1. 最后看结算失败。账本超时，数据库锁冲突，冻结记录不存在，服务崩溃，结算可能在任何一步失败。
  2. 收到成交事件，状态是 Pending。账本记账成功，就进入 Settled。
  3. 遇到可重试的错误，比如超时或锁冲突，进入 Retrying。每次重试的间隔越来越长，这叫指数退避。重试成功，同样进入 Settled。
  4. 超过最大重试次数，就进入死信。遇到不可重试的错误，比如冻结不足、数据异常，也直接进死信，不再浪费重试次数。
  5. 运营人员在后台人工排查。修复后手动重放，进入 Settled。如果判定是错误成交，就冲正。所有重试和重放都用同一个幂等键，所以重放多少次，都只记一次账。
  6. 注意，撮合已经确认的成交不能撤销。结算失败只能补，不能退回到撮合之前。结算卡住期间，用户看到订单已成交，余额却没变，界面要显示结算中。
本集小结

记住三件事

  • 结算按成交号幂等，翻译成两组平衡分录，清算中间户归零。
  • 手续费从收到的资产扣；Maker/Taker + VIP 定费率，BNB 抵扣 75 折，返佣事后批量发。
  • 结算失败只能补：退避重试 → 死信 → 人工恢复，始终同一幂等键。

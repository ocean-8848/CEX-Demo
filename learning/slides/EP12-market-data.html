行情系统不改变订单簿，是只读副本。丢一个事件 → 深度对不上 → 每个事件都带序号。
比喻：撮合引擎是球场，行情系统是转播车。比分牌 = Ticker，阵型图 = 深度，精彩回放 = K 线。
比喻失效处：转播丢几帧无所谓；行情丢一条增量，本地订单簿就错了，必须重建。
  1. 撮合引擎输出两类事件。第一类是成交事件，带价格、数量、方向和时间。
  2. 第二类是订单簿变化事件，说的是某个价格档的数量变成了多少。
  3. 成交事件决定价格走势类的数据，也就是逐笔成交、K 线和 Ticker。
  4. 订单簿变化事件决定挂单分布类的数据，也就是增量深度、有限档深度和最优挂单。
  5. 注意，行情系统不改变订单簿，它只是一个只读副本。丢一个事件，深度就和真实订单簿对不上。所以每个事件都要带序号。
  6. 打个比方，撮合引擎是球场，行情系统是转播车。比分牌是 Ticker，阵型图是深度，精彩回放是 K 线。
  7. 但比喻不完全准。转播丢几帧无所谓。行情丢一条增量，本地订单簿就错了，必须重建。
02 · 深度 Depth

深度 = 按价格档汇总的订单簿

订单簿 · 单个订单

→

深度 · 每档总量

  1. 先看深度怎么来。深度是按价格档汇总后的订单簿。它不显示单个订单，只显示每个价格的总量。
  2. 订单簿里，100.10 这一档有 S1 和 S2 两个订单。深度只显示一行，100.10，总量 2.0。
  3. 现在 S1 被吃掉 0.8。行情系统发出一条增量，100.10，1.2。
  4. 注意，1.2 是这一档新的总量，不是变化量。如果你把它当成减 0.8 去算，本地订单簿马上就错了。
  5. 再假设 S2 也被吃光。增量变成 100.10，数量 0。数量为 0，表示这一档被清空，要从本地删掉。
02 · K 线 OHLCV

逐笔成交 → 1 分钟 K 线

  1. 再看 K 线。一根 K 线，把一个时间窗口内的成交压缩成五个数。也就是开高低收和成交量，简称 OHLCV。
  2. 示例，10 点 0 分 5 秒，第一笔成交 100.10。这是新窗口，新建一根 K 线，开高低收都是 100.10。
  3. 第二笔 100.25，刷新最高价。第三笔 99.95，刷新最低价。收盘价总是等于最新的一笔。
  4. 第四笔 100.15，时间是 10 点 0 分 42 秒，还在同一分钟。收盘价变成 100.15，成交量累加到 1.4。
  5. 第五笔在 10 点 1 分 3 秒，进入新窗口。旧 K 线关闭，币安用字段 x 等于 true 来标记。新 K 线从 100.20 开始。
  6. Ticker 也来自同一条成交流。它是 24 小时滚动统计，包括最新价、最高价、最低价、成交量和涨跌幅。
02 · K 线合并

5 根 1 分钟 → 1 根 5 分钟

12 根 5 分钟 → 1 小时。某分钟无成交：不生成，或用上一根收盘价补一根零量 K 线，各系统做法不同。
迟到的成交：时间戳属于已关闭窗口 → 历史 K 线被修订 → 需要定义迟到容忍规则。
  1. 大周期 K 线由小周期合并。示例，5 根 1 分钟 K 线，合成一根 5 分钟 K 线。
  2. 开盘价取第一根的开盘价，100.10。收盘价取最后一根的收盘价，100.25。
  3. 最高价取最大，100.40。最低价取最小，99.80。成交量求和，等于 6.0。
  4. 同样，12 根 5 分钟合成 1 小时。如果某分钟一笔成交都没有，有的系统不生成 K 线。有的系统用上一根收盘价，补一根零成交量的 K 线。
  5. 还有一个坑，迟到的成交。它的时间戳属于已经关闭的窗口，会让历史 K 线被修订。生产系统要定义迟到容忍规则。
03 · 本地订单簿同步

先拉一次快照，再持续应用增量

每秒拉全量快照：太慢、太重
REST GET /api/v3/depth { "lastUpdateId": 107, "bids": [...], "asks": [...] }
快照一次 + 增量持续：又快又轻
WS <symbol>@depth { "U": 106, // 第一个更新 ID "u": 110, // 最后一个更新 ID "b": [["100.00", "1.5"]], "a": [["100.10", "0"]] // 新总量 }
  1. 接下来是本集重点。量化交易者要在本地维护一本订单簿，并且和交易所保持一致。
  2. 每秒拉一次全量快照，太慢，也太重。正确做法是，先拉一次快照，再持续应用增量。
  3. 币安公开文档给了标准步骤。REST 深度快照会返回一个 lastUpdateId，表示快照对应的更新序号。
  4. 增量深度流的每个事件带两个序号。大写 U 是本事件第一个更新 ID，小写 u 是最后一个更新 ID。
  5. 事件里还有 b 和 a，分别是买盘和卖盘的变化档位。格式是价格，加上新的总量。
03 · 按币安公开文档的步骤

同步本地订单簿

本地 ID
—
  1. 来看完整流程。第一步，先建立 WebSocket 连接，订阅增量深度。收到的事件先缓存起来，不处理。
  2. 第二步，再用 REST 请求快照。示例，快照返回的 lastUpdateId 是 107。
  3. 第三步检查。107 不小于第一个缓存事件的 U，也就是 101，可以继续。如果 lastUpdateId 比 U 还小，就重新请求快照。
  4. 第四步，丢弃 u 不大于 107 的缓存事件。101 到 105 这个事件被丢掉。
  5. 第五步，本地订单簿等于快照，本地 ID 设为 107。
  6. 第六步，应用 106 到 110 这个事件。107 落在 106 和 110 之间，对齐成功。本地 ID 变成 110。
  7. 下一个事件的 U 是 111，正好等于本地 ID 加 1，说明连续，可以应用。本地 ID 变成 115。
  8. 再下一个事件，U 是 120。本地 ID 是 115，U 应该等于 116 才对。中间缺了一段，出现了缺口。
  9. 这时不能硬着头皮继续。丢弃本地订单簿，从第一步重新开始。
03 · 顺序与应用规则

顺序反了，会丢一段事件

1u < 本地 ID → 忽略
2U > 本地 ID + 1 → 丢弃本地簿，重建
3每个价格档：数量 0 → 删除；否则覆盖，不存在就插入
4本地 ID = 本事件的 u
症状：本地出现 买一价 ≥ 卖一价 · 交叉盘口 → 立刻重建
  1. 为什么一定要先开 WebSocket，后拉快照？我们看看反过来会怎样。
  2. 假设先拉快照，拿到 107。等 WebSocket 连上，第一个事件已经从 112 开始。108 到 111 这一段，谁也没收到。
  3. 先开连接再拉快照，快照之后的事件都已经在缓存里，一条不漏。
  4. 应用每个事件时，记住四条。第一，u 小于本地 ID，忽略。第二，U 大于本地 ID 加 1，重建。
  5. 第三，数量为 0，删除这一档，否则用新数量覆盖，不存在就插入。第四，把本地 ID 设为这个事件的 u。
  6. 如果增量丢了还继续用，常见症状是买一价大于等于卖一价，也就是交叉盘口。看到它，就该重建了。
04 · 推送扇出 Fan-out · 业界通用做法

算一次，复制给几十万连接

  1. 一个热门交易对，可能有几十万个订阅者。撮合引擎不可能直接给每个客户端发消息。
  2. 行情系统用多层扇出。撮合事件进入按交易对分区的消息总线，行情计算节点只算一次。
  3. 算好的结果进入发布总线，再复制给 N 个推送网关。计算成本和订阅人数无关，带宽和订阅人数成正比。
  4. 推送网关无状态，可以水平扩容。每个网关只记住，哪个连接订阅了哪个频道。
  5. 最大的风险是慢客户端。它的发送缓冲区满了，网关应该断开它，不能让它拖慢其他人。
  6. 常见优化有四个。第一，100 毫秒或 1000 毫秒合并推送。第二，只推前几档。第三，同一条消息只序列化一次。第四，客户端按需订阅。

05 · 指数价格 Index Price · 业界通用做法

多家交易所的加权平均

代表全市场公允价格，主要给合约用
单一交易所最新价易被操纵：薄盘口砸一笔大单就偏离
① 采集 ② 剔除异常值 ③ 剔除过期 ④ 加权平均
权重与成分以币安官方公告为准
100.00×0.40 + 100.20×0.35 + 99.90×0.25
=
  1. 再看指数价格。它是多家现货交易所价格的加权平均，代表全市场的公允价格，主要给合约用。
  2. 为什么需要它？单一交易所的最新价容易被操纵。有人在薄盘口砸一笔大单，最新价就会瞬间偏离。
  3. 计算分四步。采集多家价格，剔除偏离中位数太多的异常报价。再剔除数据过期的交易所，最后按权重加权平均。
  4. 示例，A 交易所 100.00，权重 40%。B 是 100.20，权重 35%。C 是 99.90，权重 25%。
  5. 加权平均等于 100.045。标记价格在它的基础上，再加一个平滑的基差，用来算未实现盈亏和强平。第 14 集细讲。
故障与边界

延迟来自每一层

合并推送：1000ms 流天然最多晚 1 秒
极端行情消息暴增：网关积压，毫秒级 → 秒级
问题对策
REST 与 WS 不同步用 lastUpdateId 对齐，不按时间对齐
多个网关版本不同消息带序号或事件时间，客户端以序号为准
行情不是成交依据 → 以订单接口为准
剧烈波动时：你看到的是过去的价格，市价单实际成交价可能大幅偏离
  1. 现在回到开头的问题。延迟来自每一层。撮合输出、消息总线、行情计算、推送网关、公网，最后是客户端解析。
  2. 合并推送本身就有延迟，1000 毫秒的流，天然最多晚 1 秒。极端行情消息暴增，网关积压，延迟会从毫秒级升到秒级。
  3. 一致性也会出问题。REST 和 WebSocket 不同步时，用 lastUpdateId 对齐。不要按时间对齐。
  4. 多个推送网关版本不同，两个客户端可能看到不同的最新价。客户端要以序号为准。
  5. 最后一条原则，行情不是成交依据。行情显示成交了，订单接口显示没有，以订单接口为准。
  6. 所以剧烈波动时用市价单要小心。你看到的是过去的价格，实际成交价可能大幅偏离。
本集小结

记住三件事

  • 行情是撮合事件的只读副本：成交 → 成交、K 线、Ticker；簿变化 → 深度。
  • 先开 WS，再拉快照；用 lastUpdateId 与 U、u 对齐，有缺口就重建。
  • 行情一定有延迟；成交结果以订单接口为准。

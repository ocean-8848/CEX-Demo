01 · 并发模型

一个交易对，一个线程

→ A 必须先成交
收银台可以加开，
单个交易对的线程不能拆

→

→
同一本
订单簿
锁竞争 · 执行顺序不确定
  1. 撮合必须严格有序。两个订单谁先到，决定了谁先成交。这是上一集讲的时间优先。
  2. 如果多个线程同时改同一本订单簿，就得加锁。锁带来竞争，执行顺序也变得不确定。
  3. 业界通用做法是，一个交易对只由一个线程处理。交易对之间没有依赖，所以可以按交易对分片。BTC 在线程 A，ETH 在线程 B。
  4. 打个比方，每个交易对是一个收银台，只有一个收银员。他不用和别人商量，所以速度很快。
  5. 比喻不成立的地方在这里。超市排长队可以加开收银台，撮合引擎不行。热门币上线，大家都挤进同一个交易对，这条队只能越排越长。
02 · 数据结构需求

订单簿要快速完成三件事

操作频率需要的结构复杂度
找到最优价每个订单都要做有序结构 + 缓存最优档O(1)
新增价格档 · 删除空档频繁红黑树或跳表O(log n)
按订单 id 撤单非常频繁哈希表O(1)
三种结构叠在一起用：价格档有序结构 + 档内双向链表 + 订单 id 哈希索引
  1. 订单簿要高效完成三种操作。第一，找到最优价。每个新订单都要做，所以必须是常数时间。
  2. 第二，新增价格档，或者删除空档。这件事很频繁，需要有序结构，做到对数时间。
  3. 第三，按订单 id 撤单。这是最频繁的操作之一，需要哈希表，在常数时间里定位订单。三者叠在一起，就是生产级订单簿的常见做法。
02 · 内存订单簿

卖盘的内存结构

价格档 · 红黑树或跳表         档内双向链表 · 队头在左
订单 id 哈希索引
  1. 来看这三种结构怎么拼在一起。左边是价格档，用红黑树或跳表按价格排序。引擎缓存最优档的指针，读取最优价是常数时间。
  2. 每个价格档挂一条双向链表。新订单追加到链表尾部，成交从链表头部取。这正是 FIFO。
  3. 示例，新卖单 S6 挂在 100.10，数量 0.5。它直接接到 S2 后面。这一档的总量从 2.0 变成 2.5。
  4. 现在用户撤销 S2。引擎查哈希表，一步找到 S2 的节点。再把它从双向链表里摘掉，不需要遍历。
  5. 每个价格档还缓存一个总量。行情的深度数据直接读这个值，不用逐单求和。第 12 集讲行情深度时，还会用到它。
02 · 数值表示

价格和数量，全部用整数

价格 100.10 ÷ tickSize 0.01 = 10010
数量 0.5 ÷ stepSize 0.00001 = 50000

浮点数

整数 tick

1 + 2
= 3  永远精确
  1. 还有一个细节。引擎内部的价格和数量，全部用整数表示。
  2. 示例，tickSize 是 0.01。价格 100.10 就存成整数 10010。数量也按 stepSize 换算成整数。
  3. 为什么要这样做？因为浮点数有误差。在很多语言里，0.1 加 0.2 并不精确等于 0.3。
  4. 撮合差一点都不行。剩余数量会出现极小的灰尘，账就对不上。换成整数，1 加 2 永远等于 3。所以精度换算在入口完成，引擎里只有整数。
03 · 定序

先定序，再落日志，再撮合

→
定序器
seq + 时间戳
→
事件日志 · 只追加
→
撮合引擎
反过来：撮合已执行、日志没写成 → 两边不一致。日志是唯一事实来源。
  1. 现在进入本集重点。订单服务有多个入口，订单是并发到达的。谁先谁后，必须有唯一的答案。
  2. 这个答案由定序器给出。它给每条输入指令分配一个全局递增的序号。序号决定处理顺序。
  3. 定序以后，指令先写进事件日志。日志只追加，不修改。时间戳也由定序器写进指令。
  4. 然后撮合引擎按序号，一条一条处理。注意顺序，先落日志，再撮合。
  5. 如果反过来，撮合执行了，日志却没写成功，两边就不一致。所以日志才是唯一的事实来源。下游的清算、行情和用户推送，也都按序号消费撮合输出的事件。
03 · 快照 + 日志 = 恢复

事件日志 seq 1–12

  1. 光有日志还不够。日志越来越长，每次都从头重放太慢。所以引擎会定期做快照。
  2. 快照就是把整本订单簿写到磁盘，并记下对应的序号。这个示例里，快照停在序号 8。
  3. 现在，引擎处理完序号 12 以后崩溃了。内存里的订单簿全部丢失。
  4. 恢复第一步，启动一个新引擎实例，加载最近的快照。订单簿回到序号 8 的状态。
  5. 第二步，重放快照之后的日志。序号 9、10、11、12，一条一条重新执行。
  6. 重放完成，订单簿和崩溃前完全一样，校验和也一致。备用引擎还可以实时消费同一份日志，主引擎故障时直接接管。
  7. 快照间隔是一个取舍。这个示例里，有序号 8 的快照，恢复只需重放 4 条指令。间隔太长，要重放的日志就多，恢复就慢。
04 · 确定性 Deterministic

相同初始状态 + 相同顺序输入 = 相同输出

  • 不读系统时钟，时间戳由定序器写入
  • 不使用随机数
  • 不依赖哈希表的遍历顺序
  • 不用浮点数计算价格和数量
  • 撮合逻辑里不调用数据库、网络
主引擎
重放引擎
  1. 重放能成功，有一个前提，撮合必须是确定性的。相同的初始状态，加上相同顺序的输入，得到完全相同的输出。
  2. 为此要守住五条规则。第一，不读系统时钟，时间戳由定序器写进指令。第二，不用随机数。
  3. 第三，不依赖哈希表的遍历顺序。第四，不用浮点数计算价格和数量。
  4. 第五，撮合逻辑里，不调用数据库、网络这些外部服务。
  5. 守住这五条，重放日志就能得到逐字节相同的订单簿和成交记录。故障恢复、主备切换、审计对账，都靠它。在配套的撮合实验页里，点重放事件日志按钮，可以亲眼验证。
  6. 反过来，假如同价订单的先后顺序用随机数决定。重放一次，成交对象就可能变，主备从此对不上。
04 · 参考架构

LMAX：单线程也能很快

英国外汇交易所，2010 年前后公开架构
单线程业务逻辑 · 全部状态在内存
事件溯源 · 重放事件重建状态
Disruptor · 无锁环形缓冲区，替代队列
落盘、复制备机、反序列化 → 业务线程之外并行
  1. 这套思路有一个著名的参考，LMAX。它是英国的一家外汇交易所，2010 年前后公开了自己的架构。
  2. 核心是单线程的业务逻辑处理器，全部状态放在内存里。再加上事件溯源，状态可以通过重放事件重建。
  3. 线程之间用 Disruptor 传递消息。它是一个无锁的环形缓冲区，用来替代传统队列。写入方和读取方各自推进指针，不需要加锁。
  4. 日志落盘、复制到备机、反序列化，都放在业务线程之外，并行完成。
  5. LMAX 公开资料称，单线程每秒能处理数百万个订单，具体以原始资料为准。关键在于没有锁，没有磁盘等待，CPU 缓存命中率高。
05 · 精度过滤器 · 币安 exchangeInfo

不合规的订单，在撮合之前被挡住

过滤器关键字段示例值
PRICE_FILTERtickSize0.01
LOT_SIZEstepSize0.00001
NOTIONALminNotional5 USDT
  1. 引擎只处理对齐了精度的整数。那么不合规的订单在哪里被挡住？答案是进入撮合之前。
  2. 币安通过 exchangeInfo 接口公开每个交易对的过滤器。PRICE_FILTER 管价格，LOT_SIZE 管数量。NOTIONAL 管订单金额。
  3. 举个示例，tickSize 是 0.01。价格 100.123 不是 0.01 的整数倍，拒绝。
  4. stepSize 是 0.00001。数量 0.000001 不是它的整数倍，也拒绝。
  5. minNotional 是 5 USDT。价格 100，数量 0.01，金额只有 1 USDT，还是拒绝。
  6. 这些校验都在撮合之前完成。被拒的订单状态是 REJECTED，根本不会进入订单簿。这样，引擎内部只需要处理已经对齐精度的整数。
05 · Self-Trade Prevention

自己的买单碰上自己的卖单

自成交：不改变持仓，却制造虚假成交量，监管上常视为对敲
簿内 Maker · 账户 A · 卖 100.10 × 1.0
新到 Taker · 账户 A · 买 100.10 × 0.6
  1. 下一个机制，自成交预防，简称 STP。同一个账户的买单和卖单互相成交，叫自成交。
  2. 它不改变持仓，却制造了虚假成交量，监管上常被视为对敲。所以引擎发现双方属于同一账户，就按规则取消订单，不产生成交。
  3. 示例，账户 A 在 100.10 挂卖 1.0。现在 A 又下了一个 100.10 的买单，数量 0.6。看币安公开的几种模式。
  4. EXPIRE_TAKER，取消新来的买单剩余部分。EXPIRE_MAKER，取消簿里的那张卖单。
  5. EXPIRE_BOTH，两边都取消。DECREMENT，双方都扣减重叠的 0.6，不产生成交。完整的模式列表，以币安官方文档为准。
  6. 因为 STP 被取消的订单，状态是 EXPIRED_IN_MATCH。上一集的状态机里提到过它。

热门币上线的第一分钟

缓解 · 业界通用做法：仅限价单阶段 · 价格保护 PERCENT_PRICE_BY_SIDE · 单用户限频
  1. 最后看撮合引擎的局限。一个交易对只有一个线程。这个线程的处理能力，就是这个交易对的上限。
  2. 分片只能扩展交易对的数量，不能扩展单个交易对的吞吐。
  3. 热门币上线的第一分钟，最能暴露这一点。输入队列积压，用户下单后好几秒才收到回报。
  4. 价格几秒内剧烈波动，早到的市价单成交价远高于预期。撤单指令排在大量新订单后面，迟迟撤不掉。
  5. 业界常见的缓解办法有三个。上线初期只开放限价单。设置价格保护，币安有 PERCENT_PRICE_BY_SIDE 过滤器。再对单个用户限频。还要提醒一句，撤单也要排队定序，它不是即时生效的。
本集小结

记住三件事

  • 按交易对分片、单线程、内存订单簿：有序价格档 + 双向链表 + 哈希索引。
  • 先定序，再落日志，再撮合；崩溃后加载快照，重放后续日志。
  • 一切依赖确定性：不读时钟、不用随机数、不用浮点数。

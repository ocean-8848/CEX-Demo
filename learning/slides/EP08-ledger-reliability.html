重启、重投、超时之后，账还能不能对？

  1. 先看一个场景。结算服务让账本给用户 A 记一笔成交，账本写成功了。可是返回结果的时候，网络超时了。
  2. 结算服务不知道成功没有，于是重试。同一笔成交，第二次到达了账本。如果账本照单全收，用户 A 就多拿了一份 BTC。
  3. 上一集我们讲了双分录。可这两次记账，每一次自己都是借贷平衡的。平衡校验发现不了这个错误。
  4. 所以这一集讲账本的可靠性。系统重启、消息重投、网络超时之后，账还能不能对？

01 · 至少一次投递 At-least-once

为什么账本一定会收到重复请求？

  1. 先说清楚，为什么重复请求一定会出现。交易所的消息系统，通常是至少投递一次。消息可能到达一次，也可能到达多次，但不会一次都不到。
  2. 来看时序。结算服务调用账本，要求记一笔成交 T1。账本记账成功。
  3. 可是响应在网络里丢了。上游等到超时，它没法区分，是请求丢了，还是响应丢了。
  4. 最安全的做法就是重试。于是 T1 第二次到达账本。所以，重复是常态，不是意外。账本必须自己扛住重复。

  1. 来看动画。示例：用户 B 卖给用户 A 0.04 BTC，成交号 T1，暂不计手续费。左边的账本关闭幂等，右边开启幂等。
  2. 第一次投递，两边一样。A 的 BTC 从 0 变成 0.04，B 从 1 变成 0.96。
  3. 现在 T1 被重投了。左边照单全收，又记了一遍。A 变成 0.08，B 变成 0.92。买方多收币，卖方多扣币。
  4. 右边开启了幂等。账本发现 T1 的幂等键已经存在，直接返回第一次的结果，不再记账。余额保持不变。
  5. 注意左边的错误。每一笔分录自己都平衡，资产等于负债加权益也还成立。能发现它的，只有幂等键，以及撮合和结算之间的对账。
01 · 业务唯一键 Idempotency Key

执行 1 次和执行 N 次，结果相同

① 上游生成键来自业务
② 同一事务写流水 + 写键
③ 唯一索引数据库兜底
④ 键已存在返回第一次结果
idempotency_key = "spot_trade:quote:T1001" -- UNIQUE INDEX
✓ 成交号；充值交易哈希 + 输出序号
✗ 随机数、时间戳：每次重试都会变
  1. 幂等，就是同一个请求执行一次和执行 N 次，结果相同。做法是给每个资金动作，带一个业务唯一键。
  2. 第一步，上游生成唯一键。比如现货成交的计价资产分录。键由 spot_trade、quote 和成交号拼起来。
  3. 第二步，账本在同一个数据库事务里，写入流水和这个键。第三步，数据库对这个键建唯一索引。
  4. 第四步，如果键已经存在，账本返回第一次的结果，不再记账。
  5. 注意，唯一键必须来自业务。比如成交号，或者充值交易哈希加输出序号。不能用随机数或者时间戳。它们每次重试都会变，等于没有幂等。
02 · append-only · 示例

充值 100 USDT，被误记成 1000，怎么改？

UPDATE … / DELETE …　已写入的分录不能改、不能删
用户 A 余额 · USDT
✓ 任意时刻余额可回放
✓ 审计看到错误与纠正
✓ 快照坏了可重建
  1. 第二段，流水只追加。示例：用户 A 充值 100 USDT，程序却记成了 1000。现在发现了，怎么改？
  2. 第一反应是改那一行，或者删掉重记。但账本流水是只追加的。已经写入的分录，不能更新，也不能删除。
  3. 正确的做法，是写一笔冲正分录。方向相反，金额相同，并且引用原来那一笔。1000 被抵消，余额回到 0。
  4. 然后再写一笔正确的分录，充值 100。余额变成 100，和事实一致。
  5. 这样做有三个好处。任何时刻的余额，都能从第一条流水回放出来。审计员能看到，错误发生过，也被纠正过。快照坏了，也能从流水重建。
03 · 余额快照 Snapshot

快照是缓存，流水才是事实

记账事务同一事务
写流水 entries
更新快照 balances
Σ 流水 = 余额快照内部对账 ①
每个资产 Σ借 = Σ贷内部对账 ②
中间户余额 = 0内部对账 ③
快照 ≠ 流水 → 以流水为准重建快照
中间户不归零 → 找卡住的结算，补偿或人工
  1. 每次都从全部流水求和，太慢了。所以系统维护余额快照。每次记账时，在同一个事务里顺手更新它。
  2. 快照对不对，要靠对账来检查。对账，就是用独立的数据源，检查余额是否一致。
  3. 第一类是内部对账，检查三个等式。流水求和等于快照。每个资产借方合计等于贷方合计。中间户余额等于 0。
  4. 快照和流水不一致，就以流水为准，重建快照。中间户不归零，就去找卡住的结算，补偿或者人工处理。注意，方向永远是从流水推出快照，而不是反过来。
03 · 三方对账 Reconciliation · 示例数字

账本 vs 链上 vs 托管方

内部对账

数据源：内部账本
Σ借 = Σ贷✓
流水和 = 快照✓
中间户 = 0✓

账链对账

数据源：账本 + 链上节点
账本热钱包
链上余额
充值在途

账托对账

数据源：账本 + 托管报告
账本冷钱包3000 BTC
托管方报告3000 BTC
差额0
红色告警 → 暂停该币种提币 → 人工排查：冲正 / 补单
  1. 内部对账只看了账本自己。可是账本说热钱包有多少币，链上真的有吗？这就要三方对账。
  2. 三个独立的数据源，内部账本、链上数据、托管方报告。一个源出错，另外两个源能发现它。内部对账先通过。
  3. 账链对账，比较账本里的热钱包资产，和链上地址余额。示例：账本 500 BTC，链上 502 BTC。多出的 2 BTC，是链上已出块、账本还没入账的充值，记在在途账户里。
  4. 账托对账，比较账本里的冷钱包和托管资产，和托管方的报告。示例：两边都是 3000 BTC，相等。
  5. 如果哪一天，链上只剩 480 BTC，账本还是 500，差了 20。业界通常的做法是，先暂停这个币种的提币，再人工排查，冲正或者补单。
03 · 局限

对账能发现问题，但不能替你定位

只知道不等

不告诉你哪一笔错了，定位靠流水回放

有延迟

对账周期内的错误，先影响用户，再被发现

PoR 是时点

只证明某一刻资产 ≥ 负债，不证明没有隐藏负债
币安未公开账本数据库选型与分片方式 → 本集所讲为业界通用做法，不代表币安具体实现
  1. 对账很重要，但它有三个局限，我们要讲清楚。
  2. 第一，对账只能发现不等。它不会告诉你是哪一笔错了。定位要靠流水回放，一笔一笔往回找。这也是为什么，流水必须完整，必须只追加。
  3. 第二，对账有延迟。对账周期之内发生的错误，会先影响用户，然后才被发现。
  4. 第三，储备金证明只证明某一时刻，资产大于等于负债。它不证明平台没有其他隐藏的负债。
  5. 补充一点。币安没有公开账本的数据库选型和分片方式。这一集讲的是业界常见设计，不代表币安的具体实现。
04 · 热点账户 Hot Account

所有成交都要写同一行

  1. 第四段，热点账户。每一笔成交，都要给平台手续费收入账户，记一笔贷方。
  2. 币安这样的大所，每秒有大量成交，具体数字没有公开。这些事务都要更新同一行余额快照。数据库行锁开始排队，吞吐量被这一行卡死。
  3. 打个比方。商场有 100 个收银台，所有收银员都要跑到同一个保险柜存钱。保险柜门口一定排长队。
  4. 解决办法是分桶。把手续费账户拆成 N 个子账户，按成交号哈希选一个桶。示例里是 4 个桶，并发写冲突大约降到原来的四分之一。
  5. 后台的定时任务，再把各个桶汇总进总账。就像每个收银台先放个小钱箱，下班再统一存进保险柜。比喻不准的地方是，汇总也要记分录，也要带幂等键。
04 · 两种业界通用解法

只给平台账户用，不给用户账户用

方法做法代价
分桶拆成 N 个子账户，按成交号哈希选桶查总额要把 N 个桶相加
异步汇总成交只写流水，后台每 T 秒汇总进快照快照有 T 秒延迟
用户账户不分桶、不异步：余额必须实时准确，否则会超额下单
思考：64 个桶求和 vs 读汇总表，数值什么时候会不同？
  1. 业界常用两个办法。第一个是刚才的分桶。代价是查询总额时，要把 N 个桶加起来。
  2. 第二个是异步汇总。成交时只写流水，不更新快照。后台每隔 T 秒，把新流水汇总进快照。代价是快照有 T 秒的延迟。
  3. 注意，这两个办法只用于平台账户。用户账户一般不分桶，也不异步。用户余额必须实时准确，否则会出现超额下单。
  4. 留个思考题。手续费分成 64 个桶以后，运营要查今天的手续费收入。直接加 64 个桶，和读汇总表，数值什么时候会不一样？
05 · Transactional Outbox

账记了，消息却丢了？

下游：推送余额风控额度数据仓库
错误做法
COMMIT 记账✓ 已落库

发消息 MQ✗ 永远没发出
Outbox
同一事务流水 + 快照 + outbox 事件
发布器轮询未发布事件
消息队列
标记published_at
流水、快照、事件同一事务提交：要么全部成功，要么全部失败 → 事件不会比账本少
  1. 最后一段，outbox 模式。账本记完账，要通知下游。比如推送余额给用户，更新风控额度，写入数据仓库。
  2. 错误的做法是，先提交数据库事务，再发消息到消息队列。
  3. 如果进程正好在这两步之间崩溃，账已经记了，消息却丢了。用户的余额变了，界面和风控却不知道。
  4. outbox 的做法是，在同一个数据库事务里写入三样东西。流水、快照，和一条 outbox 事件记录。三者要么全部成功，要么全部失败。
  5. 然后由独立的发布器轮询 outbox 表，把还没发布的事件发给消息队列。发布成功后，标记发布时间。
05 · Outbox 的另一面

不丢，但可能重 → 下游去重

可能重复

发完消息、标记之前崩溃 → 重启后再发一次

按事件 ID 去重

下游消费端幂等

死信

重试超过上限 → Dead Letter → 人工处理
至少一次投递 + 消费端幂等 = 效果上恰好一次
必须告警：outbox 表堆积 → 消息队列或发布器故障
  1. outbox 解决了丢，但带来了重。发布器可能发完消息，还没来得及标记，就崩溃了。重启以后，同一个事件会再发一次。
  2. 所以下游必须按事件 ID 去重。你会发现，这又回到了幂等。至少投递一次，加上消费端幂等，是整套系统的基本组合。
  3. 发布失败时，发布器记录重试次数。超过上限，事件进入死信，交给人工处理。
  4. 还有一个必须告警的指标，就是 outbox 表堆积。它说明消息队列或者发布器出了故障。堆积越久，用户看到的余额就越旧。
本集小结

记住三件事

  • 重复是常态：每个资金动作带业务唯一键，唯一索引兜底。
  • 流水只追加，错了冲正；三方对账不平，先停提币再排查。
  • 热点平台账户分桶或异步汇总；事件走 outbox，下游去重。

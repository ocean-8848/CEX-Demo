高可用 · 业界通用做法

状态不同，高可用策略也不同

  1. 先看高可用。这是一个双机房的布局。用户先到全局流量调度，再分到两个机房。
  2. API 网关没有本地状态，可以多活。两个机房都接流量，用负载均衡分流。
  3. 撮合引擎不同。订单簿在内存里，必须严格有序。所以是单主加热备，按交易对分片。热备消费同一份有序事件流，订单簿和主节点保持一致。
  4. 账本存的是资金余额，要强一致。主库同步复制到另一个机房。业界常见的取舍是，撮合同机房求低延迟，账本跨机房求强一致。
  5. 现在机房 A 故障。流量调度把用户切到机房 B，撮合热备接管成为新主，账本从库提升为主库。
  6. 最危险的情况是脑裂。主备同时认为自己是主，两个撮合引擎同时成交，就会重复成交。
  7. 所以要用租约或仲裁服务，保证同一时刻只有一个主。这是客机比喻不准的地方。两个机房可能互相看不见，必须靠第三方来裁决。
撮合主备切换 · 示例序号

快照 + 有序指令日志 = 可重建的订单簿

  1. 撮合引擎把订单簿放在内存里。进程一退出，内存就没了。所以必须能从持久化数据重建。
  2. 重建靠两样东西。快照，是某一时刻订单簿的完整副本。指令日志，是快照之后的全部指令，按序号严格排序。
  3. 正常时，主节点不断写入指令，热备一直跟着回放。举个示例，主节点写到1005，热备回放到1003。
  4. 这时主节点心跳超时。仲裁服务确认它失联，撤销它的租约，再把租约授予热备。
  5. 热备先把日志补齐到1005，再校验订单簿哈希。然后宣布成为主节点，从1006开始接收。
  6. 订单服务会重发没收到确认的指令。新主按序号去重，1004和1005直接跳过。没有序号，同一笔订单就可能成交两次。
  7. 没有热备时，就是冷启动。加载最近的快照，再回放之后的全部日志。日志越长越慢，所以要定期生成快照。
降级策略

按影响范围逐级降，恢复时反向开

L0正常运行
L1限流降低 API 配额
L2暂停充提链节点异常、对账不平
L3只读模式撮合或账本异常
L4全站维护需要停机修复
恢复顺序查询→撤单→下单→充提
只读期间：行情不能继续推旧价格
暂停充提期间：链上充值照样到，恢复后补扫区块
  1. 部分故障时，系统要主动降级。关掉非核心功能，保护核心功能。
  2. 降级按影响范围从小到大排。第一级是限流，降低 API 配额。
  3. 第二级是暂停充提。触发条件是链节点异常，或者对账不平。
  4. 第三级是只读模式，禁止下单，触发条件是撮合或账本异常。需要停机修复时，才进入全站维护。
  5. 恢复顺序反过来。先开放查询，再开放撤单，然后开放下单，最后恢复充提。这样用户先看到真实余额。
  6. 注意两个坑。只读期间，行情服务不能继续推送旧价格。暂停充提期间，链上充值照样会到，恢复后必须补扫这段区块。

服务挂了，用户马上发现。资金对不上，可能几天后才有人发现。
  1. 第二段，怎样尽早发现问题。可观测性，就是通过系统输出的信号，判断系统内部的状态。信号有四类。
  2. 指标回答现在怎么样，比如下单延迟 P99。日志回答发生了什么，比如每次后台操作的审计记录。
  3. 链路追踪回答慢在哪里。一笔订单从网关到结算，每一段耗时都看得到。告警回答谁需要立即处理。
  4. 注意，交易所最重要的告警不是服务挂了，而是资金对不上。服务挂了，用户马上发现。资金对不上，可能几天后才有人发现。
  5. 所以告警要分级。P1 是资金错误和账实不一致，立即呼叫值班。P2 是核心交易受影响，示例15分钟内响应。P3 在工作时间处理。

  1. 第三段，怎样不被攻破。安全纵深，就是设多层独立防线。攻击者必须全部突破，才能碰到用户资产。
  2. 第一层是网络层，让攻击者进不来。比如 DDoS 防护、WAF，核心服务不暴露在公网。
  3. 第二层是账户层，让盗号者拿不走。2FA、设备绑定、提币白名单，新地址提币还要延迟。
  4. 第三层是密钥层，让黑客和内鬼签不了名。冷热钱包分离，MPC 或多签，加上硬件安全模块。热钱包只放日常提币需要的一小部分资产。
  5. 第四层是内控层，让单人做不成恶。高风险操作一人发起、一人审批，这叫四眼原则。权限要最小化，客服能查信息，不能改余额。
  6. 最后一条底线。任何人，包括管理员，都不能绕过账本直接改余额。否则审计和对账就失去了意义。

  1. 第四个案例，最早也最经典，2014年的 Mt.Gox。它曾是全球最大的比特币交易所。
  2. 根因是没有定期的账实对账。热钱包被长期持续盗取，账本余额和链上余额长期不符，多年没人发现。

  6. 核心问题是账和实脱节。如果每天对一次链上余额和账本余额，第一天就能发现异常。这也是定期对账制度的直接来源之一。

账本隔离 · 储备金证明 · 示例数字

资产 ≥ 用户余额总和，怎么证明？

默克尔树：每个用户可验证自己的余额被计入总负债。FTX 事件后，币安等交易所定期发布。
局限：只证明某一时刻；快照前可临时借入资产；不能证明没有隐藏负债 → 还需要独立审计
客户资产隔离：平台自有资金亏损，不传导到客户资产
  1. 为什么账本隔离和储备金证明这么重要？来看一组示例数字。
  2. 用户在账本里的余额加起来，示例是100亿美元。这是平台对用户的负债。
  3. 储备金证明要证明，平台持有的资产大于等于用户余额总和。示例里平台持有105亿，覆盖率105%。
  4. 如果客户资产被挪用，账面上用户还有100亿，平台实际只剩60亿。覆盖率60%，挤兑一来就兑付不了。
  5. 储备金证明用默克尔树，让每个用户都能验证自己的余额被计入了总负债。FTX 事件后，币安等交易所开始定期发布。
  6. 但它有局限。它只证明某一时刻，平台可以在快照前临时借入资产。它也不能证明平台没有隐藏负债。所以完整的保障还需要独立审计。
  7. 客户资产隔离补上另一半。平台自有资金亏了，也不会传导到客户资产。

记住三件事

  • 资金不能错；错了要能发现、能恢复。可用性排在后面。
  • 撮合靠快照 + 有序日志切换和重放；降级逐级升，恢复反向开。
  • 账本隔离、每日对账、储备金证明决定用户会不会买单。

  3. 第三，可观测性有盲区。告警只覆盖已知的故障模式，FTX 式的内控失败不会触发任何技术告警。
  4. 第四，人是最弱的一环。技术防线必须假设，某个员工的账号会被攻破。
  5. 小结三点。第一，资金不能错，错了要能发现、能恢复。可用性排在后面。
  6. 第二，撮合靠快照加有序日志来切换和重放。降级逐级升，恢复时反向逐级开。
  7. 第三，账本隔离、每日对账和储备金证明，决定了出事以后用户会不会买单。

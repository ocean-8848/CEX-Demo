# 幕后核心：用户看不见的防线

> 前置：主线 01–13 章，建议同时读过 [产品深潜](../products/README.md) 中的 P01、P03。
> 本系列讲解合规、安全、对账、风控、金库和应急响应。B01–B07 讲每道防线是什么；B08–B12 是进阶篇，讲这些防线怎样落成工程、怎样适配各地监管，以及历史上它们是怎样被突破的。它们不产生收入，但决定交易所能不能活下去。

## 1. 一句话理解

交易所前台的每一个按钮背后，都有一组看不见的检查。这些检查回答四个问题：

1. **这个人能不能用？**（合规）
2. **这个操作是不是本人？**（账户安全）
3. **这笔钱算得对不对？**（对账）
4. **这件事会不会让平台亏钱或违法？**（业务风控、金库）

当以上检查全部失效时，还有最后一道防线：**应急响应**。

> 🎯 打个比方：前台像机场的值机柜台，乘客只看到"办理登机牌"。幕后有护照查验（合规）、安检（安全）、行李追踪（对账）、塔台调度（风控）、燃油储备（金库）和消防队（应急响应）。乘客看不见它们，但少了任何一个，飞机都不能起飞。

## 2. 纵深防御总图

下图以"一次提币"为例，展示它依次穿过哪些幕后防线：

```mermaid
flowchart TD
    U["用户点击提币"] --> L1
    subgraph L1["第 1 层 · 账户安全 B03"]
        A1["登录风险评分"] --> A2["2FA 或 Passkey"] --> A3["敏感操作冷却期"]
    end
    L1 --> L2
    subgraph L2["第 2 层 · 合规 B01"]
        C1["KYC 等级与限额"] --> C2["制裁与地理筛查"] --> C3["KYT 地址风险"] --> C4["Travel Rule 信息"]
    end
    L2 --> L3
    subgraph L3["第 3 层 · 业务风控 B05"]
        R1["提币风控评分"] --> R2["营销奖励与受限资产检查"]
    end
    L3 --> L4
    subgraph L4["第 4 层 · 资金正确性 B04 和 B06"]
        F1["账本余额与冻结"] --> F2["对账状态正常"] --> F3["热钱包水位充足"]
    end
    L4 --> L5
    subgraph L5["第 5 层 · 平台安全 B02"]
        S1["签名策略引擎"] --> S2["MPC 或 HSM 签名"]
    end
    L5 --> OUT["广播上链"]
    L1 -. "任一层发现严重异常" .-> IR["应急响应 B07"]
    L4 -.-> IR
    L5 -.-> IR
```

读图要点：

- 每一层只拦截自己负责的风险。单独一层都会漏，叠在一起才可靠。
- 第 4 层"对账状态正常"是很多人忽略的一环：如果账本与链上对不平，系统应该停止该币种提币（见 B04）。
- 第 5 层是最后的技术防线。2025 年 Bybit 事件说明，签名人看到的界面本身也会被篡改（见 B02）。
- 虚线表示升级路径：任何一层发现严重异常，都会触发应急响应。

## 3. 四类幕后系统的关系

```mermaid
flowchart LR
    subgraph Prevent["事前：阻止坏事发生"]
        B01["B01 合规"]
        B02["B02 平台安全"]
        B03["B03 账户安全"]
    end
    subgraph Detect["事中：发现坏事"]
        B04["B04 对账"]
        B05["B05 业务风控"]
    end
    subgraph Absorb["事后：承受和修复"]
        B06["B06 金库与流动性"]
        B07["B07 应急响应"]
    end
    Prevent --> Detect --> Absorb
    Absorb -- "复盘改进规则" --> Prevent
```

读图要点：

- 事前防线成本高、会影响用户体验，所以不可能拦住所有风险。
- 事中检测用数据发现漏网之鱼。对账针对"算错"，风控针对"做坏事"。
- 事后系统决定一次事故是"可控损失"还是"平台倒闭"。FTX 倒闭的直接原因，是没有可用的储备承受挤兑。
- 复盘把事故教训写回事前规则，形成闭环。
